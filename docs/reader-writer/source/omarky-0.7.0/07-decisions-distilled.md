# omarky decisions and principles, distilled for a port

Source repo is `/home/p0werj0int/Projects/omarky` (version 0.7.0). Each entry gives what omarky decided, the behaviour it protects, and a verdict.

- **portable** means the decision carries over as written, independent of stack.
- **adapt** means the goal carries over but the means must change, and the entry says how.
- **stack-only** means the decision exists because of omarky's toolkit and has no meaning in a different stack. The behaviour it protects may still be specified elsewhere.

---

## Part A. README principles

- **DEC-P1 The page.** One centred column about 68 characters wide. Line height and paragraph spacing give the text room. Bullets, numbers, heading marks and quote marks hang in the left margin so the text keeps one straight edge. Headings scale from the body size, and whitespace binds each heading to the text it introduces (`README.md:13`). Verdict **portable**. Specified in `01-page-and-typography.md` PAGE-21 to PAGE-31 and PAGE-54 to PAGE-69.
- **DEC-P2 The type.** iA Writer Quattro S for prose, its Mono S for code, the same family in bold for headings. The mono is lighter than a programmer's font and has no ligatures, so a code block sits beside a paragraph without shouting and shows exactly what the file says (`README.md:14`). Verdict **portable** (the fonts are files any stack can load).
- **DEC-P3 The colours.** The current Omarchy theme, read live as it switches, light or dark. Code colours are generated from the theme's own colour set (`README.md:15`). Verdict **adapt**. Derive every page role (dim, faint, ghost, hairline, washes) from the host app's fg, bg and accent with the same mix and alpha factors, and generate the syntax palette from the same theme in memory. Whether the source is Omarchy's colors.toml or the host app's own theme is a host choice.
- **DEC-P4 The chrome.** A header with the file's name, an outline that follows you, and the page. Keys do the rest. `?` shows the shortcuts (`README.md:16`). Verdict **portable**. Note the README's claim that the writer's header steps aside while typing and returns on mouse move is only partly true in code (see `04-writer-behaviour.md`).
- **DEC-P5 The file.** Plain Markdown. The reader reloads in place when another program changes the file, keeping your position. The writer saves exactly what you typed (`README.md:17`). Verdict **portable**.
- **DEC-P6 Versions.** With a git history, pick any earlier version and see what changed, marked on the page as you read (`README.md:18`). Verdict **portable** as a feature. See DEC-0012 and DEC-0013 for the boundary.
- **DEC-P7 The craft claim.** "Omarky sets a Markdown file the way a typesetter sets a page." A well-set page is one where you start reading and an hour passes (`README.md:11`). Verdict **portable**. This is the acceptance test for every visual choice.

## Part B. Decision records

- **DEC-0001 Flat block list in a virtualised view.** The document is one flat array of top-level blocks with source line maps, nested content inside each block. The view builds only what is on screen plus a cache of two screens, because building every block of a 1,100-block file up front cannot open in under a second. Parsing a 5,400-line file takes about 40 ms (`docs/decisions/0001-flat-blocks-in-a-listview.md:1-11`). Verdict **adapt**. Keep the flat block list with source maps (it drives reload anchoring, copy-source, edit ranges, find and progress). Replace the toolkit list with whatever virtualisation the renderer offers, using estimated heights for unbuilt blocks and the two-step travel (RD-24) to land exactly.
- **DEC-0002 Raw HTML is recognised, never rendered.** Parse with HTML on so comments can be hidden. Drop comment-only HTML, show an unclosed comment rather than swallowing the file, show all other HTML literally in muted mono, turn `<br>` into a line break, and turn image-only HTML into a centred wrapping gallery (`docs/decisions/0002-raw-html-recognised-never-rendered.md:1-21`). Verdict **portable**.
- **DEC-0003 Select faces by style name, not weight.** The installed Quattro S Bold file declares the regular weight, so a weight-based request rendered every paragraph bold. Prose asks for the "Regular" style by name, and inline bold and italic still resolve to the real faces (`docs/decisions/0003-quattro-s-regular-style-name.md:1-8`). Verdict **adapt**. The hazard is real for any font matcher that trusts the OS/2 weight. Load the four Quattro S face files explicitly (Regular, Bold, Italic, Bold Italic) and map bold and italic runs to them by file, with a test that a plain paragraph renders in the Regular face.
- **DEC-0004 Own autolink matcher and footnote plugin.** The bundled autolink matcher never matched under the JS engine, so omarky wrote its own, linking scheme URLs, `www.` hosts and e-mails, trimming trailing punctuation, keeping balanced parentheses, never linking bare domains like `file.md`. Footnotes are collected into one block numbered by first citation, unreferenced notes after (`docs/decisions/0004-own-linkify-and-footnotes.md:1-16`). Verdict **adapt**. The engine bug is stack-only. The autolink rules and footnote numbering are portable behaviour, so check the chosen Markdown crate's autolink and footnote output against them and post-process where it differs.
- **DEC-0005 Headings in Quattro S Bold on a 1.25 scale.** Duo and Mono bold read as shouting next to Quattro body text. Mono is kept for structure (alert titles, badges, table headers). h1 +3 steps, h2 +2, h3 +1, h4 +0.5, h5 body size in dim, h6 small capitals tracked (`docs/decisions/0005-heading-font.md:1-10`). Verdict **portable**. Note the code sets h6 at body size, not smaller (PAGE-14).
- **DEC-0006 Syntax colours generated from the theme.** Code colours come from the page theme's own palette so a code block matches its page, with a fixed role mapping (keywords magenta, functions blue, strings green, numbers orange, types yellow, built-ins cyan, operators dim, comments faint italic, errors red) (`docs/decisions/0006-ksh-themes-from-colors-toml.md:1-26`). Verdict **adapt**. The on-disk theme files and the startup generation are stack-only. Generate the highlighter's style table in memory from the current theme and rebuild it on theme change, which also removes omarky's limitation that themes added after launch fall back to stock colours.
- **DEC-0007 Code in iA Writer Mono S at 0.84 × body, leading 1.5.** JetBrains Mono was heavier with a taller x-height and has ligatures, wrong for a reader that must show exactly what the file says. The Nerd Font is kept for icons only (`docs/decisions/0007-code-font.md:1-10`). Verdict **portable**.
- **DEC-0008 Warnings are bugs, with a two-item allowlist.** Any runtime warning fails the screenshot run. Only two categories that are not the app's and cannot be fixed (a vendor lint and a portal registration line) are filtered (`docs/decisions/0008-log-rules.md:1-16`). Verdict **adapt**. The specific categories are stack-only. Keep the rule that the headless renderer and scripted checks fail on any warning or error log line, with an explicit, commented allowlist for external noise.
- **DEC-0009 Scrolling budget and highlighter warm-up.** Measured by scrolling a 5,400-line file in 120 px steps, forcing synchronous layout each step. Mean step under 1 ms, worst 18 to 19 ms once per run. The spike came from first-use compilation of each code language mid-scroll, fixed by warming the document's languages one every 40 ms after open. No item reuse, cache of two screens (`docs/decisions/0009-scrolling-performance.md:1-19`). Verdict **adapt**. Keep the measurement (a bench command that steps the scroll and reports worst and mean) and the budget (worst step under one 60 Hz frame, mean well under). Whether warm-up is needed depends on the highlighter, so measure first.
- **DEC-0010 Window behaviour choices.** Find counts over document-order text pieces so it covers unbuilt blocks, and paints matches inside the text (current one solid accent). Live reload keeps the same block by source text, falling back by source line. A deleted file stays on screen under a banner, polled every second. Reduced motion is the compositor's animations-off switch or an env flag, and every duration goes through one gate. Ctrl+O uses the native file chooser. Text never takes key focus. Right-click, Ctrl+Shift+C and Ctrl+Shift+A copy source. Zoom and 20 recents persist, test runs never write them (`docs/decisions/0010-window-behaviour-choices.md:1-32`). Verdict **portable** except the file-chooser mechanism, which is **adapt** (use the platform portal chooser).
- **DEC-0011 Touchpad scrolling matched to Chromium.** The toolkit moved one pixel per compositor unit and never flung, so a swipe went a twelfth as far as in the browser the user's touchpad curve was tuned for. omarky moves 12 px per unit and flings on Chromium's curve, dv/dt = −3.7 (v + 172), from the last three frames' velocity when the lift comes within 200 ms of the last movement. A wheel notch glides 120 px. The toolkit's own flick handling is off so nothing moves twice (`docs/decisions/0011-touchpad-scrolling.md:1-27`). Verdict **adapt**. The goal (a swipe travels as far as in the user's browser, with the same fling feel) is portable. The 12× factor depends on what unit the windowing layer delivers, so measure the raw delta per swipe in the new stack and calibrate against the same browser before copying 12.
- **DEC-0012 Changes is a mode of the reader, not an app.** A file with git history grows a versions chip in the header. Picking a version marks what changed on the page. The outline marks the current section by shading alone, no accent bar (`docs/decisions/0012-changes-as-a-mode-of-reading.md:1-22`). Verdict **portable**. Details are in `06-changes-mode.md`.
- **DEC-0013 Version resolution stays behind a boundary.** The window never runs git. A separate launcher resolves a spec such as "danny fri" to a version and hands the window one job of two texts, two labels and the history, so the spec grammar lives in one tested place and other version sources can be added without touching the window (`docs/decisions/0013-git-behind-the-launcher.md:1-19`). Verdict **adapt**. Keep the boundary as a module or crate interface (version source in, two texts and labels out) rather than a separate process, unless process isolation is wanted.
- **DEC-0014 The editor is plain text, painted.** The writer's editor holds the file's Markdown character for character and only paints formatting (sizes, faded marks, hanging indents, line height). Rich-text rebuilding moved the cursor and split paragraphs, and block-per-paragraph editors broke Enter and Backspace (`docs/decisions/0014-native-highlighter.md:1-23`). Verdict **adapt**. The rule (the buffer is the file, formatting is paint, marks hang in the margin) is portable. The native highlighter module is stack-only.
- **DEC-0015 Layout is outside undo.** Line layout (height, hanging indent) is never an undo step, so undo and redo only move text. Typing `- ` then undo removes the text in one step and never gets stuck reapplying the indent (`docs/decisions/0015-layout-outside-undo.md:1-17`). Verdict **portable** as behaviour, with that exact round-trip as the test. The private-flag mechanism is stack-only.
- **DEC-0016 The editor lives in the shared library, optional extras.** One editor component serves the writer and the reader's edit sheet, reading none of the writer's settings, and works plainly without the native painting module (`docs/decisions/0016-the-editor-in-the-library.md:1-20`). Verdict **adapt**. Build one editor widget used by both the writer surface and the reader's sheet, configured by the host. The optional-native-module fallback is stack-only.
- **DEC-0017 A shared library both apps vendor.** Code shared by reader and writer lives in a third repository, vendored as a submodule (`docs/decisions/0017-omarky-the-shared-library.md:1-18`). Verdict **stack-only**. In a single Rust workspace the equivalent is a shared crate.
- **DEC-0018 Editing happens in a sheet over one block.** E opens the block under the pointer (Shift+E its section) in a card over the page, neighbours faint around it. Ctrl+Enter splices the edited lines into the source and writes the whole file atomically, after checking the source has not changed underneath. The page itself never becomes editable. In changes mode the sheet offers the older wording of a reworded block with a "Use this" chip (`docs/decisions/0018-a-sheet-edits-one-block.md:1-22`). Verdict **portable**. Details are in `05-edit-sheet-and-rewrite.md`.
- **DEC-0019 Rewrite with Claude, no tools.** Ctrl+J opens an instruction line under a block, section or selection. A separate process builds the prompt (with an optional style guide and an optional check script whose failure report is fed back), runs Claude Code with no tools so it cannot touch the file or machine, and returns text. The window applies it as one undo step. Billing is the user's Claude subscription. Users without Claude Code never see the line. The whole document is sent, and the README says so (`docs/decisions/0019-claude-behind-the-launcher.md:1-24`). Verdict **adapt**. Keep the boundary (job in, text out, no tools, one undo step, hidden when the CLI is absent). Run it as a subprocess from Rust. Re-check the model constant and env scrubbing for the new host.
- **DEC-0020 A click on a task box ticks it in the file.** One character on the marker line changes, the file is written atomically, and the page shows the change only via reload. A stale line is refused with a toast. Clickable only when the page is the file on disk (`docs/decisions/0020-task-boxes-tick-in-the-file.md:1-18`). Verdict **portable**.
